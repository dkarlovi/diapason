# Action hierarchy and interaction-state consistency

**Verdict:** The studio has a coherent visual identity and a sound Download-first
hierarchy. Its interaction system does not reliably separate what is running,
what is applied, what is merely being auditioned, and what an action will change.
The next work should consolidate those meanings across existing controls.

## Evidence and scope

Read-only review of the current working tree, including the previously requested
Download/Play changes. No application or design-system files changed in this run.
The two assessments were isolated until A completed. Parent-operated Chromium
captures used separate fresh design and technical contexts/tabs.

The final design context captured 26 states; the technical context captured 24.
Desktop was 1280×900 in light mode; phone was 390×844 in dark mode. Browser states
include Library audio/MIDI playback, editor audio/MIDI playback, preset/key/
instrument auditions, preview switching and stopping, Use, applied-and-previewed
options, custom preset, metronome preview, clap listening, and phone audition.
The design context completed room/sound checks, count-in/recording, and saving
with a synthetic microphone. Technical capture did not proceed beyond tempo:
Confirm remained disabled after insufficient clap sampling; this is a test
limitation, not a demonstrated product defect. Both contexts had zero observed
page exceptions. Real microphones, listening quality, physical phones, screen
readers, Web MIDI hardware, and the full theme/device combination matrix were
not tested.

## Design specificity and strengths

The paired original/interpreted timeline, preserved audio, audition workflow,
live signal and calibration belong to this product. Restrained Slate & blue is
appropriate; a new visual identity would not address the issues below.

- Download is primary and labeled on both tracks; mobile preserves its label.
- Preview and Use are genuinely separate operations, and preview switching,
  stopping, and applying worked in the inspected states.
- Shared dropdown rows, accessible transport names, state attributes, live
  status regions, and tuning categories provide a reusable foundation.

## Priority findings

1. **P1 — Phone auditions hide the thing being evaluated.** Observed in
   `/tmp/diapason-interactions-complete/design/26-phone-preset-preview.png`.
   Tune and the candidate menu cover nearly all the roll and most of the
   temporary-preview status. Users hear a candidate but cannot inspect its note
   changes or easily establish its commitment state. `EditorTools.tsx:57` starts
   preview without closing Tune; mobile layout is in `editor.css:479`.
   **Rule/fix:** starting an audition exposes the comparison canvas, candidate
   identity, temporary/applied state, and Stop. Provide a short route back to
   candidates. This restores the existing documented mobile audition agreement.
   Suggested command: `/impeccable adapt`.

2. **P2 — Running controls use different visual and verbal contracts.** Browser
   observed: Library playback and tempo preview turn blue; editor Stop remains
   neutral; dropdown preview retains the word Preview and a starting-action
   accessible name while its square icon means Stop. Applied and previewing
   rows share a blue fill, differentiated mainly by a thin outline.
   `Library.tsx:40`, `TempoSetup.tsx:45`, `EditorCanvas.tsx:90`,
   `PreviewOption.tsx:26`, `editor.css:637`.
   **Rule/fix:** Download stays primary blue; passive previews are secondary;
   running playback/audition controls share amber feedback and name the next
   action Stop, visibly and accessibly. Applied selection keeps a separate blue
   treatment and explicit state text. Recording Stop retains its distinct red
   recording treatment. Hue reinforces labels rather than carrying meaning alone.
   Suggested command: `/impeccable polish` with shared-state scope.

3. **P2 — Applied and temporary status sometimes describe the wrong thing.**
   Browser observed: Custom (from Gentle fix) still checks Gentle fix even
   though using that row clears overrides. Previewing already-applied Gentle fix
   also announces Not applied. `MelodyPresets.tsx:12,33`,
   `useMelodySettings.ts:33`, `EditorCanvas.tsx:119`.
   **Rule/fix:** Applied denotes the exact effective configuration. Identify the
   base preset separately from the current custom configuration. Previewing and
   Applied are independent states that can coexist. State whether Use would
   replace custom adjustments instead of implying the checked row is identical.
   Suggested command: `/impeccable clarify`.

4. **P2 — Audition feedback depends on the setting being previewed.** Browser
   observed: preset/key auditions identify a candidate and temporary state,
   but instrument audition of the full melody says Playing note in context.
   Octave shares the same source route. `PlaybackSettings.tsx:48`,
   `useEditor.ts:318`, `EditorCanvas.tsx:118`.
   **Rule/fix:** every audition carries its subject, candidate and commitment
   state into consistent status text. Reserve Note in context for that operation;
   instrument/octave previews should name the candidate without changing exports.
   Suggested command: `/impeccable clarify`.

5. **P2 — Field labels conceal immediate reset actions.** Screenshots show
   label-like Preset, Key, Instrument, Octave and slider captions. Source confirms
   those buttons reset and persist values; Preset reset can discard overrides.
   Footer Reset instead asks for confirmation. The reset mutation was inspected
   in source, not activated in the browser run. `MelodyDropdown.tsx:17`,
   `MelodyKnob.tsx:62`, `MelodyPresets.tsx:18`, `EditorTools.tsx:68`.
   **Rule/fix:** distinguish labels from actions, expose reset scope, and make
   replacements recoverable. Prefer an explicit scoped Reset affordance with
   undo; if label-click remains a shortcut, it must not be the only visible
   indication of reset behavior. Suggested command: `/impeccable clarify`.

## Proposed shared interaction vocabulary

| Meaning                   | Treatment                                                                  |
| ------------------------- | -------------------------------------------------------------------------- |
| Primary output            | Blue Download; visible label.                                              |
| Available preview         | Secondary Play/Preview.                                                    |
| Running playback/audition | Amber feedback; Stop with subject; not inferred only from color.           |
| Applied value             | Explicit Applied/check with blue selection treatment; exact configuration. |
| Preview candidate         | Named candidate and preview state; say whether it differs from applied.    |
| Recording                 | Existing red Stop and count-in/recording feedback.                         |
| Replacement/reset         | Explicit scope and an appropriate recovery path.                           |

## Cognitive load, emotion and personas

Moderate cognitive load: grouping and progressive disclosure are helpful, but
menu choices and action hierarchy are weak points. Users must decode checked,
outlined, running, temporary, and custom states while comparing sound. Do not
treat eight grouped preset candidates as eight required simultaneous decisions.
The emotional valley follows a promising audition: uncertainty about what is
applied and whether Use/Reset will discard previous adjustments.

- Jordan, first-timer: a checked base preset can look like the exact applied recipe.
- Sam, accessibility-dependent user: a pressed Play name describes the opposite
  of the next action; reset button names omit their effect. Screen-reader
  behavior itself was not tested.
- Casey, distracted phone user: the audition canvas/status is covered, and
  hover-only reset explanations are unavailable.
